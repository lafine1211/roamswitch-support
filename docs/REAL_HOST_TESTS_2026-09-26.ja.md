# 実機の試験 2026年9月26日

Dockerのスイートには、systemdも、fanotifyの許可イベントも、同じEthernetセグメントの別の機器もありません。
これらがある環境で試験しました。スクリプトは [`../test/realhost`](../test/realhost) にあります。

## 環境

- 被験機: Ubuntu 24.04(aarch64)のVM。カーネル 7.0、systemd 255。Mac上で、実際の有線LANにブリッジ接続し、
  それぞれが自分のMACを持ちます。ゲートウェイは実際のルーターです。その日のソースから作った `.deb` を、
  `dpkg` で入れました。同じセグメントに、攻撃側のVMを置きました。
- 物理のx86_64のUbuntu 24.04(カーネル 6.8)を1台。古い版でした。
- macOSでは、実施していません(「実施していないこと」)。

## Linuxクライアントへの偽のARP(lockdown)

| ケース | 結果 |
|---|---|
| 別の機器から、ゲートウェイを名乗る偽のユニキャストARP応答を15回。ゲートウェイの項目は動的 | 「ARP cache change on stable network session」を記録し、約1秒でAir-Gapが発動。記録は `arp_spoof_lockdown`、phase は `full`、信頼済みのMACを保存 |
| 同じ攻撃。ゲートウェイのARP固定がオン(項目は `PERMANENT`) | 影響なし。カーネルが固定した項目を保ち、検知も遮断も起きない |
| 攻撃をやめたあとの解除 | 自動。約11分後(既定の10分のあと、60秒にわたる3回の確認)。ゲートウェイのMACが信頼済みのものと確認できた |
| 原因が解消したと確認できないときの、`--force` なしの `roamswitch emergency-restore` | 実行しない(端末がなければ終了コード2)。いまのMACと信頼済みのMACを表示。`--force` があれば、ファイアウォールのテーブル、記録、ARP固定、DNS、接続追跡を戻し、ゲートウェイに再び届く |

## 無害な、複数アドレスの機器(この試験で見つかったこと)

1台の機器が、1つのMACで2つのIPに答える状態(ここでは、別名アドレスを持つ攻撃側のVM。仮想マシンを動かすPC、
別名を持つNASと同じ形)は、ゲートウェイへの攻撃ではありません。

| 版 | 結果 |
|---|---|
| 修正前 | lockdownで「ARP SPOOFING DETECTED in lockdown」となり、偽装したパケットが1つもないのに、全面のAir-Gapが発動した。解除の判定も、その重複を「偽装がまだある」と数えていた(コードから読んだ内容。下の物理の機械が解除されなかったことと合う) |
| 修正後 | 通知(10言語)だけで、遮断しない。重複が残ったまま、偽のゲートウェイARPを送ると、約1秒でAir-Gapが発動し、約11分後に自動で解除(隔離 15:56:46、解除 16:07:46) |

物理の機械は、古い版で、最初の偽の応答でAir-Gapに入り、1時間以上たっても隔離されたままでした。その横のMacと、
ブリッジ接続したVMが、この重複を作っていました。遠隔からは解除できず、コンソールでの復旧(`sudo roamswitch emergency-restore --force`)が要ります。

## 隔離の記録と、サービスの再起動

`RuntimeDirectory=roamswitch` のため、systemdがサービスの停止時に `/run/roamswitch` を削除し、隔離の記録(原因、確度、開始時刻)も
消えていました。`dpkg -i`、再起動、クラッシュのあとで、高確度の隔離が、「不明」の低確度の隔離として作り直され、
10分で自動解除されました。`RuntimeDirectoryPreserve=yes` にすると、`systemctl restart roamswitch` の前後で、
記録(`arp_spoof_lockdown`、同じ開始時刻)が同じでした。

## 偽装した送信元のSYNスキャン(1ケース200個、Linuxクライアント)

| 偽装した送信元 | 検知 | 遮断 | 理由 |
|---|---|---|---|
| デフォルトゲートウェイ | する | しない | SYNが、ゲートウェイの近隣エントリと違うMACから届いた |
| 同一リンクの別の端末 | する | しない | そのアドレスのMACが解決されておらず、実在の機器が答えていない |
| リンク外のアドレス | する | しない | リンク外なのに、フレームがゲートウェイのMACから来ていない |
| このホスト自身のアドレス | しない | - | カーネルが捨てる |
| 実在の、MACを解決できるスキャナー(対照) | する | する(10分) | |

既定で拒否のプロファイルでは、SYNが黙って捨てられるので、MACが解決されない送信元は、遮断されません。
安全な側に倒れます。

## 実機のカーネル(fanotify)でのランサムウェアの挙動

1つのプロセスが、監視対象のフォルダーで、64KiBの40ファイルを書き換える。「失った数」は、凍結されるまでに書き換えられた数。

| ケース | この日の修正の前 | 修正後 |
|---|---|---|
| 全体を暗号化、通常のプロセス名 | 検知して凍結。40個中31個を失った | 同じ |
| 全体を暗号化、プロセス名を `python3` に設定 | **検知できず**。40個すべてを失った | 検知して凍結 |
| 全体を暗号化、プロセス名を `git` に設定 | **検知できず**。40個すべてを失った | 検知して凍結 |
| 部分暗号化(32バイトのうち16バイト) | 検知できない | 検知できない |
| 暗号化した内容をBase64で書く | 検知できない | 検知できない |
| 本物の `python3`、`cp -r`、`rsync -a`、`tar -x`、`makepkg` という名前のbashスクリプトが、ランダムな40ファイルを書く | `python3`、`cp`、`rsync`、`tar` が、『不明なプロセス』のバーストとして通知された(各1〜2件) | 検知しない |

誤った通知は、短時間で終わるツールが、ワーカーの判定より先に終了していたためです。書き込みを見た時点で、
書き手を識別するようにしました。名前の確認は、実行ファイル(またはインタープリタが動かすスクリプト)が名前と
一致することも求めます。本当に `git` という名前のバイナリや、本物の `python3` で攻撃者のスクリプトを動かすと、
今も除外されます。名前は境界ではありません。

## GTKアプリを、実際に操作した結果

アプリを、VMの中の専用の仮想ディスプレイで動かし、そのディスプレイのスクリーンショットを取りました。
リンク保護タブに、DNSトンネリングの除外ドメインの欄が、保存した値とともに出ています。Tailscaleのバックエンドを選んだVPNタブには、
WireGuardの行がありません。Exit Nodeを入力すると、「（なし — 保護オフ）node1.example.ts.net」が保存されました。
ラベルが名前の一部になっていました(修正済み)。ネットワークタブの解除ボタンは、確認なしに解除していました(修正済み)。
解除のダイアログは、原因、状態、解除の前に確認すること、ゲートウェイのMAC、ボタンを有効にする承認のチェックを表示します。

## 実施していないこと

- **macOSのアンインストーラの、通しの確認**。肝心の手順(ヘルパーのデーモンとシステム拡張の登録解除)は、システム設定での承認が要り、
  アンインストール自体も、モーダルのダイアログから始まります。macOSのVMで、GUIの操作は、システムの許可の確認で止まりました。
  人が答えないと進みません。
- **上の機械以外のx86_64のパッケージ**。ここでの試験は、aarch64です。
- **実際のLANでの、ゲートウェイのMACの複製**。ルーターと同じMACを持つ機器を置くと、実際のスイッチが混乱します。
  MACの比較では見分けられません(ホワイトペーパー)。測っていません。
- **第三者による再現**。
