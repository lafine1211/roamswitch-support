## AccessScope

A security diagnosis tool for access logs. It is a separate app (Apache-2.0): the Server Edition .deb / .rpm packages carry only the command (`accessscope`; from 1.11.2 they also carry the PersonalSOC and PathScope commands); the Linux client edition and the Mac app carry the command and a window app.

### 0.3.7

- **Changed: the order and names of the Settings tabs now match PathScope and PersonalSOC.** The app's own tabs come first, and the three shared tabs come last, in the order "LLM integration", "Display language" and "Update". AccessScope is now "Analysis", "Exclusion rules", "LLM integration", "Display language" and "Update", and the first tab you see when you open Settings is "Analysis" (the guide that leads you to LLM integration still opens the "LLM integration" tab directly). The French label for "LLM integration" is now "Intégration LLM", like the others.
- **Changed: the desktop app can now also run the LLM analysis as root** (the same as the command line). When running as root, Settings shows a notice: "it runs with root privileges, so running as a user without privileges is recommended (agy and codex cannot be stopped from running commands)". Before, it said it was unavailable.
- **Changed: the `--trust-forwarded-for` note is now one line for the total, not one per log read.** "N lines had their client IP decided from X-Forwarded-For" was repeated once per log read (117 lines for 117 logs), even for logs with a count of 0, and filled the end of the diagnosis with the same sentence. It is one line in the summary table in the table output, and one line at the end with `--plain`. The per-log counts stay in the input log list of the Markdown report and in SARIF.

### 0.3.6

- **Changed: for logs behind a reverse proxy or a Docker gateway, the real client is now decided automatically.** Only for lines whose recorded source is an internal address (loopback, private, link-local, CGNAT), `X-Forwarded-For` is read from the right, and the first address that is not a trusted relay becomes the client (the same idea as nginx's `real_ip_recursive`). Before, 127.0.0.1 and 172.x.0.1 were listed as attack sources (found while diagnosing a production Ubuntu server). It is not applied to lines that came directly from outside. If every value is an internal address (a request from the host itself), the original address stays. The number of lines resolved this way appears in the report. To turn it off, use `--trust-forwarded-for=off` (in the window, choose "Do not use" under "Analysis" in Settings; the choices are "Automatic (default)", "Do not use", "From the right" and "Leftmost").
- **Changed: an IP decided from a header is not treated as a verified crawler.** This prevents an attacker from writing a crawler's official IP in `X-Forwarded-For` and calling itself `Googlebot` to escape the reconnaissance and high-rate findings. It is the same with the automatic rule and with `--trust-forwarded-for`. A line that came directly from an official IP is verified as before.
- **Fixed: internal addresses no longer form a "multi-stage attack chain".** An internal address is a row that merges many clients, not the action of one attacker (on a real server, 127.0.0.1 and the Docker gateway had become chains rated high).
- **Fixed: chains with no sign of success are now rated low, and the list shows at most 10.** On a real server 74 chains were listed and buried the point. The rest is given as a count ("N more"), and all of them are in `--report` and the JSON. A chain with a suspected success or a web shell is still rated high, and all of them are shown.
- **Fixed: a redirect (301, 307 and so on) to an uploaded script is no longer counted as a web shell being used.** A request that only got a redirect had made a chain high (web shell). A 200 response is still counted as before.
- **Fixed: the Apache logs on openSUSE are now found** (`/var/log/apache2/access_log` and the config `/etc/apache2/httpd.conf`).
- Verified by reading real Apache and nginx logs in containers of Fedora, Rocky Linux 9, openSUSE Leap 15.6, Arch and Debian 13 (on Fedora, with nginx in two tiers, the automatic resolution of `X-Forwarded-For` too).

### 0.3.5

- **Added: detection of XSS in headers and of out-of-band (OAST) callback hosts.** Misses in the XSS detection were measured against publicly documented techniques and closed. The 229 payloads of an XSS testing tool were run through six encodings and through the User-Agent and Referer headers. In the query (as is, URL, double URL, HTML entity encoding) detection went from 218/229 to 229/229; in User-Agent and Referer from 1/229 to 229/229 (XSS used to be left out of the header detection). Obfuscated calls after leaving a string (`window['ale'+'rt']`, `(alert)(1)`, `eval(atob(..))` and so on) and calling `alert` with a template literal in backticks were added. For headers, the body patterns are not applied; only a strict check is made: a tag, a `javascript:` call, a call after an event attribute, or a bare `alert(1)` shape. Something that is only a search term in the browser's Referer is lowered to a low-confidence hypothesis.
- **Added: a new kind, `web_oast`.** It finds callback hosts of interactsh (`oast.pro`, `oast.live`, `oast.site`, `oast.online`, `oast.fun`, `oast.me`, `interact.sh`) and Burp Collaborator (`oastify.com`, `burpcollaborator.net`). A random subdomain is required, and paths such as `/scripts/interact.sh` are not matched. In a header it is reported as `web_header_attack(oast)`.
- **Fixed: one false positive.** A parameter whose name starts with `on` and whose value is only a function name (a normal script URL setting), such as `onload=onloadCallback`, was reported as `web_xss` at high.
- 53 cases (`xss_ext.jsonl`) were added to the evaluation data: attacks and benign look-alikes. The known gaps of the existing evaluation (14) and the false positives on normal traffic did not increase.

### 0.1.0 - 0.3.4 (summarized)

The contents of these releases, grouped by theme. The full text of each entry is in this file's git history.

- **First release** (0.1.0): from web server access logs (Apache and Nginx common/combined, nginx / Caddy / Traefik JSON, gzip) and SSH authentication logs (sshd logs, and journald on Linux) it finds attack attempts and shows them with the evidence log lines, the MITRE ATT&CK technique ID and a confidence level (confirmed, likely, hypothesis). It is read-only: it never changes logs and never raises privileges. The analysis uses neither an LLM nor the network. The Mac app can update itself (Settings → Update); on Linux it is updated by the package.
- **What it finds** (0.1.0): SQL injection, path traversal, XSS, command and code injection, Log4Shell, Shellshock, template injection, SSRF, exploit paths of known vulnerabilities (Apache 2.4.49/50, PHPUnit, Laravel Ignition, Citrix, FortiOS, Spring4Shell, Confluence, Exchange and others), probing for secret files and admin pages, attack-tool User-Agents, mass attempts on non-existent paths, login brute force and distributed attempts (credential stuffing), web-shell-like access, chains from reconnaissance to attack, high-rate requests, SSH brute force, user-name probing, a success after failures and root password authentication, and instructions to an AI planted in logs. 0.2.0 added the User-Agents that HexStrike AI announces, httpx, CensysInspect and the api-recon bundled with ARTEX.
- **Fewer misses and false alarms** (0.2.0): measured on our own labelled test data (982 attack cases and 292 normal-traffic cases as of 0.2.0; the data grew during the work). Attack detection went from 83.3% to 99.1% overall, and from 15.7% to 98.6% on hard variants such as encoding and obfuscation. The share of normal traffic that raised a finding of medium severity or higher went from 30% to under 2% (5 of 292). These are figures on our data and do not guarantee the result on your logs.
- **Resistance to evasion** (0.2.0): before matching, it undoes repeated URL decoding (up to 3 times), alternative Unicode forms (fullwidth forms, overlong UTF-8, `%uXXXX`), SQL comments, `${IFS}` and nested Log4j lookups. The evidence line shown in a report stays the original log line. Numeric spellings of addresses in SSRF URLs (hex, decimal, octal, short forms) are read too. A line over 24 KiB is no longer dropped silently: it is analysed from its first and last parts, and the number of such lines is shown in the findings and the input list.
- **A CVE rule pack** (0.2.0): exploit attempts that are recognisable from the request line and appear in CISA's KEV (the catalog of known exploited vulnerabilities) are matched against a data table with sources: 64 rules covering 71 CVEs, dated 2026-10-08. The date and rule count appear at the top of the report, in the JSON and in `--version`, and a finding lists the CVEs it matched. A match means the request had the shape of an exploit; it does not mean the attempt succeeded.
- **Detections over time windows** (0.2.0): login brute force (windows of 1 hour, 1 minute and 14 days), login spraying, SSH spraying (`ssh_spray`), distributed probing by IPs that mostly get 404, and site-wide floods (`web_flood_dist`). A success after SSH failures is counted in the preceding 1-hour window too. When sshd writes two lines for one invalid-user attempt, it is counted once.
- **Judging the effect of an attack** (0.1.0, 0.2.0): an HTTP 200 is not treated as success (0.1.0). If a 2xx response to an attack-looking request is the same size as the normal page, it is reported as "the payload was probably ignored" and does not raise the severity. The overall risk (0 to 100) is weighted per kind of finding, so the number of attacking IPs does not inflate it. In 0.2.0 the response size alone is no longer used: a 2xx to an attack-looking request is rated high, medium or low by where the payload sits and who sent it (a script or a browser); for example, a browser sending it in a search parameter is medium / hypothesis. If normal responses from the same path already come in 3 or more sizes, a different size is not treated as evidence. No rule removes a finding; the reason for a lowered severity or confidence is added to the detail as a sentence.
- **Kinds of logs** (0.2.0): more logs can be read: authentication logs of sudo, su, PAM and login, fail2ban, HAProxy (HTTP and TCP), AWS ALB and CloudFront, Postfix and Dovecot, and MySQL, MariaDB and PostgreSQL, with 16 kinds of findings added. An IP that fail2ban already banned is noted on the other findings. Checked against logs captured on real Debian 12, Rocky Linux 9, HAProxy, MariaDB, MySQL and PostgreSQL. sshd logs are read from the macOS unified log (a fixed command, `/usr/bin/log show`, run by absolute path, without a shell and with an empty environment; only members of the admin group can read it). Docker container logs can be read too (on Linux, `json-file` log files are also searched; `docker logs` is used only when you choose "Also check Docker containers" in the window and confirm the commands and targets shown, or when you pass `--docker` on the command line; the only commands that can be built are `logs` and `ps`, environment variables such as `DOCKER_HOST` are not inherited and the socket is pinned to this machine, so a remote Docker is never contacted).
- **Log discovery** (0.1.0, 0.2.0): besides the standard locations it checks the places named by nginx, Apache, Caddy and Traefik configs (including rotated files) and, on Linux, journald (0.1.0). Optionally an LLM is given only facts about the environment (names of running servers, log locations named in configs, file names such as under `/var/log`; never file contents) and suggests missing locations. A suggestion is shown only after it has been confirmed to be readable as a log, and nothing is read until you choose to add it. 0.2.0 shows a result list: the verdict for each of the standard locations, config files, logs named in configs, journald, the unified log, Docker and LLM suggestions (a log that a config names but that does not exist is shown as such instead of being dropped silently, and when nothing is found the reason is given in a sentence). The list of found logs is saved (0600, up to 200 entries) and restored at the next start with the time of the last search, and all entries are checked again. The "Review what will be sent" button was removed from "Find logs with an LLM" in the window (the explanation of what is sent stays; `discover --show-prompt` on the command line remains, and the review feature in the LLM analysis panel is unchanged).
- **Analysis by an LLM** (0.1.0, 0.2.0): optional, off by default. Only a summary and a few evidence log lines are passed to an LLM (claude, opencode, codex, agy) to write a report. Raw logs are not sent; secrets are masked and IPs are defanged (or pseudonymized). `--show-prompt` shows exactly what would be sent. Logs are attacker-controlled, so text that looks like instructions to an AI is reported as a finding and the LLM output is treated as an untrusted quotation. It is not run as root. When enabled, a summary can be sent to an external service through the LLM command you chose (0.1.0). In 0.2.0 the instructions to the LLM say how to reach a conclusion on each finding: one of "confirmed", "can be ruled out (with the reason taken from facts)" or "undetermined", and something that could not be confirmed is never written as "no problem".
- **Suppression, comparison and export** (0.2.0): `--trust-forwarded-for` (off by default) takes the client IP from X-Forwarded-For (rightmost or leftmost) for logs behind a reverse proxy; the header can be forged, so it is not used by default, and it can also be chosen under "Analysis" in Settings. Suppression rules are a TOML file that names IPs, User-Agents, paths or finding kinds; a reason is mandatory and an expiry (`expires`) can be set; a high-severity finding is never hidden unless `allow_high = true`; suppressed findings are not thrown away, their count and reasons appear in the report (`--show-suppressed` lists them); `suppress.toml` in the settings folder is read automatically, and in the window you can add an entry from a finding's IP with "Suppress this IP…". Verified crawlers are told apart by checking IPs against the ranges the vendors publish officially (a snapshot from 2026-10-07; no network access); a verified crawler is left out of the reconnaissance, enumeration, scanner, high-rate and error findings and is counted instead, and a client that claims to be a crawler but comes from outside the range is reported as `web_fake_crawler` (low). For comparison with the previous run, `--state` and `--since-last` store only fingerprints of findings (a hash of kind, IP and classification) with counts and times, and split the result into new, continuing and gone since last time; with `--new-only` and `--fail-on`, the exit code is 3 only when there is a new finding; the state file is 0600 and discarded after 90 days. `--export-blocklist` writes a blocklist for fail2ban, nftables, ipset, nginx, Apache or CSV (it only writes: nothing is run and no traffic is blocked; IPs of official crawler ranges, IPs covered by suppression rules and private or documentation ranges are left out, and the header records the generation date, source logs, criteria, count and a warning). `--format` also offers CSV (with a leading formula character neutralised), SARIF 2.1.0 and JSON (the JSON carries `schema_version` and follows a versioned specification). The window can export too ("Export…").
- **Screens and languages** (0.1.0, 0.2.0): the screens and the command line are in 10 languages (the texts added in 0.2.0 too; translations are machine-made and have not been reviewed by native speakers). In 0.2.0 the input log list shows the number of long lines, the number of lines whose client IP came from X-Forwarded-For, and a note for formats that have no header columns; the top of the results shows the CVE rule pack date and rule count and the date of the crawler IP ranges; Settings gained "Analysis".
- **Activity across logs, logins from unfamiliar sources, changes from the usual** (0.3.0): the activity of one address that appears in two or more logs is shown as one time-ordered chain (`actor_chain`; the only link is the identical address, and the text says it is not proof of the same person or tool). A successful login from a source that had no successful login in the previous 30 days, for an account with an established baseline, is reported too (`ssh_new_source_login` and the like; low, hypothesis; medium when failures came first or the address appears in other logs). Changes of the recent period against the earlier part of the same log are reported (`web_new_ua`, `web_new_path`, `web_path_shift`; always low, hypothesis; `--baseline-period`, `--state` and `--since-last`). Suppression rules gained `user` (only for the three unfamiliar-source login kinds). When Docker cannot be used, the reason is shown. The "diagnose logs" screen was reorganised and technical terms were removed from the Docker explanation.
- **Measured effect** (0.3.0): the thresholds are judgement calls checked on our own evaluation data and were not tuned on real traffic. Attack recall stayed at 99.1% (1006 of 1015) and benign cases with a medium or higher finding were 5 of 312. Analysing 3.3 million lines took about 6% more time and about 1% more memory. Integration tests confirm that the same log always gives the same result. The new text is in 10 languages (based on machine translation).
- **Korean and Chinese terms unified** (0.3.1): the words for "severity" and "confidence" were aligned in the Korean and Chinese windows and reports. Korean confidence is now "확신도" (it was confusable with "신뢰" of trusted proxies). In Simplified and Traditional Chinese, "严重度/嚴重度" became "严重程度/嚴重程度", the confidence level "有力" became "较可能/較可能", and the severity "中等" became "中". What is detected and how it is judged is unchanged.
- (0.3.2) **Changed: the terminal output was tidied.** It no longer lists every log it read one by one. It counts them per kind (for example "Read 47 logs (Web access log 38, ...)") and names only the logs that could not be read. Add `--list-sources` to list them all. Findings that may have succeeded (a login after brute force, a web-shell-like request that got a success response, a login from an unfamiliar source) are named by number on a "Check first" line above the list. A note that applied to several findings is now printed once as a footnote (※1) at the end. Findings of the same attack chain are listed under one heading, one line per IP. The Markdown report (`--report`) opens with a table of all findings (number, severity, confidence, title, count) and the "Check first" line, and a long list of logs it read is counted per kind in the same way. In Japanese, the confidence levels are now shown as 高 / 中 / 低 (high / medium / low) instead of the old 確定 / 有力 / 仮説, which were unusual and hard to understand. The heading reads "[深刻度 高/確度 低]" (severity high / confidence low), and the output carries a one-line explanation of what confidence means. The labels in the other languages are unchanged. What is detected and how it is judged are unchanged. The text is in 10 languages.
- (0.3.3) **New: clients that behave very differently from the other visitors** (`web_ml_outlier`). It finds clients that no signature explains but that behave very differently from the other visitors of the same log: a scraper that keeps walking articles in order, a client walking the IDs of `/api/orders/N`, a client hammering a search API. For each client with at least 30 requests it computes 14 features (peak requests per minute, number of different paths, share of static files, share of requests with a Referer, how regular the gaps between requests are, and so on), compares them with the median and the spread of the same log, and reports only clients that are far away in two or more unrelated ways. A client that is extreme in only one way is not reported. There is no trained model, no network use, and the same log always gives the same result. The text says what differs, with the client's value and the usual value. Severity is always low and confidence a hypothesis (monitoring tools, your own app's API clients and people saving a site with `wget` look the same; these IPs are never put into the blocklist). Not candidates: clients that already have a reason (a signature hit, a scanner, 404 enumeration, login guessing, a flood), known crawlers and clients that call themselves a bot (`bot`, `crawler`, `spider`, `+http`), and clients that only repeat a few paths at a steady pace (monitors, health checks, feed fetches). If fewer than 30 clients can be compared, nothing is said and the report says why (`behavior` in the JSON). Limit: a scraper that behaves like a browser is not found (it fetches the static files, sends a Referer and keeps human-like gaps). Measured on simulated logs that we wrote (not real traffic): on 40 logs not used for tuning, all 114 unwanted automated clients were reported and none of 39,057 human visitors. It is weaker on small sites of about 100 visitors (31 of 41 fast scrapers, 15 of 39 slow ones). The existing evaluation data is unchanged (attack recall 1006/1015, 5 of 312 benign cases with a medium or higher finding). Time on 3.3 million lines is unchanged; memory grows by about 40 MB (310 MB to 351 MB). An Isolation Forest (a forest of outlier-finding trees) was also tried and not adopted because it did not reduce false reports. The new text is in 10 languages (based on machine translation; not reviewed by native speakers).
- (0.3.4) **Changed: the command line can now run LLM analysis as root too** (like PersonalSOC). It used to refuse `--llm` as root. `sudo accessscope scan --llm NAME` works. **What an LLM reads is written by attackers (log lines, user names, URLs). `agy` and `codex` cannot be stopped from running commands, so as root they run with root's rights** (`accessscope llms` shows the tool-lock state of each LLM). To keep the LLM away from root, run the diagnosis as root with `--show-prompt` (it sends nothing and prints the whole text for the LLM) and hand that text to the LLM as an unprivileged user. The window app still does not run LLM analysis as root. Diagnosis without `--llm` already worked as root.
- (0.3.4) **Changed: the terminal output is now Markdown tables.** In this order: an overview table (overall risk, logs read, summary lines), "Check first", the findings table (number, severity, confidence, finding, count, main sources), a table of multi-stage attack chains (one row per IP) and a table of notes. Chains stay in one table however many there are. The evidence log lines and the full explanation of each finding are not in the list; they are in the Markdown report (`--report FILE`). `--plain` prints the previous sentence-style list. The window app and the Markdown report are unchanged. The table headings and similar text are in 10 languages (based on machine translation; not reviewed by native speakers). What is detected and how it is judged is unchanged.

## PathScope

### 0.1.9

- **Changed: the command output is now Markdown headings and tables.** It prints, in this order, an overview table, a table of paths, a table of fix points (priority, steps, reason, affected paths), the detail of each number (ATT&CK, the fix command in a code block, notes), the scope of collection and the assumptions of the analysis. "What if I fixed this" (`--what-if-*`) and the comparison with last time (`--baseline`) are also bulleted. The assumptions of the analysis now appear in the result instead of on standard error. Pass `--plain` to get the previous sentence style. Collected strings such as file names are neutralized so that they cannot break the tables or the code fences. **If a script reads the output as text, add `--plain` or read the JSON (`--json-out`).**
- **Added: `--help` now describes every option** (analysis, output, comparison with last time and hypothetical analysis, scheduled runs and CI, the exit codes and examples; 10 languages). Before, it printed a single line of usage. `--version` (`-V`) was added too.
- **Changed: the order and names of the Settings tabs now match AccessScope and PersonalSOC.** The app's own "Export", "Continuous checks" and "Permissions" come first, and the shared "LLM integration", "Display language" and "Update" come last (the former "LLM" and "Language" labels became "LLM integration" and "Display language"; the names are aligned in 10 languages).

### 0.1.8

- **New: the local privilege escalation CVE data now includes CVEs that are easy to exploit even if they are not in KEV.** The selection widened from "listed in KEV" to "listed in KEV, or EPSS (the predicted probability of exploitation) was 0.5 or more at any point in the last 30 days". EPSS comes day by day from FIRST's official API. It selects by the maximum in the 30-day window, not the current value, because the EPSS of a new CVE is high right after publication and drops sharply within weeks (on 2026-09-24, the two Dirty Frag CVEs also fell from the 0.9s to the 0.02s). The existing conditions (Linux kernel, sudo and so on; local, high confidentiality and integrity, privileges not HIGH in NVD) apply to CVEs entering through EPSS as well. The 50 existing KEV-based entries were not reduced. Three were added (CVE-2023-22809 sudoedit, CVE-2026-43284 and CVE-2026-43500 Dirty Frag). Dirty Frag can be matched with real fixed-version information from Debian, Ubuntu, RHEL and SUSE. A CVE added only through EPSS does not widen the "confirmed distributions and versions" coverage. The wording on screen no longer says flatly "exploited in a real attack"; it now says "or is likely to be exploited" (10 languages; other than Japanese and English they are machine translations without native review).
- **New: a CVE once added through EPSS stays even if its EPSS falls.** If a CVE whose EPSS stayed low after the window dropped out, it would vanish before kernel updates had spread, and a machine that has not been fixed would look "fine" (Dirty Frag would have disappeared in the update of the week of 2026-10-26). A CVE leaves only when you put it in the exclusion list, when NVD's scoring changes so that it no longer meets the conditions, or when it moves because it was listed in KEV. If NVD or a distribution's data merely could not be fetched, the previous entry stays. There is no expiry. A kept entry carries a note that it was kept, the date it first entered, and the highest EPSS so far (the on-screen note says this too, in 10 languages).
- **Changed: the weekly data update now lists, in the job summary, CVEs whose coverage shrank compared with last time.** Replaying the real data showed that SUSE's public data became unavailable for 2026 CVEs, which would silently shrink the SUSE and Leap coverage by 18 each for two KEV-based CVEs (a change on the source side that we cannot fix). The diff check was split out into a script with unit tests.

### 0.1.7

- **Updated: the known-vulnerability data is now the CISA KEV catalog 2026.10.04 (data generated 2026-10-05).** This is the data used by the check of installed software versions against known vulnerabilities (0.1.5); until now it was the 2026.10.02 catalog (generated 2026-10-04). The vulnerability entries in the data are the same as before; only the catalog version and the generation date changed. The data date shown in the result is newer, which gives more time before the notice that appears when the data is over 45 days old. The data is bundled with the app, and nothing is looked up over the network during an analysis. There are no other changes.

### 0.1.0 - 0.1.6 (summarized)

The contents of these releases, grouped by theme. The full text of each entry is in this file's git history.

- **Added: PathScope can now be bundled in RoamSwitch's Linux packages (deb, rpm and tarball) on Linux.** It installs a launcher entry and icons so that it opens from the application menu, the `pathscope` command, the `pathscope-gui` window and the Apache-2.0 texts. An install made by a package does not use Settings > Update; it says that updates come with that package's updates. (0.1.4)
- **Fixed: on Linux (WebKitGTK) in dark mode, a closed drop-down kept a white background and its text was unreadable.** (0.1.4)
- **Fixed: depending on the startup order, the text in the update section could stay as a raw key name.** It could happen when the update information arrived before the text catalog was loaded (on both Mac and Linux). (0.1.4)
- **Changed: even with "unrestricted", private key files and API key or password values are not sent.** Until now, choosing "unrestricted" turned off both the replacement of values and the exclusion of files such as private keys. From now on, the following are kept whatever the setting. Private key files (a renamed key, or a key pasted into a config file, is found by its content, `-----BEGIN … PRIVATE KEY-----`). API keys in well-known formats (AWS, GitHub, Slack, OpenAI/Anthropic, Google, GitLab, npm, Stripe, JWT, `Bearer`), passwords inside URLs, and values whose name means a password or key (`name=value`, `name: value`, JSON, `--name value`) are replaced with `[REDACTED]`. What "unrestricted" still turns off is the exclusion of things like password hashes and `.env`, and the guess that treats long alphanumeric strings as secrets. Because this works by names and shapes, some secrets can still be missed. （0.1.2）
- **Fixed: the German label for "unrestricted" is now "Uneingeschränkt".** The earlier "Unbegrenzt" reads as "unlimited in quantity". The settings screen now matches the wording on the website and in the EULA. （0.1.3）
- **Fixed: even in standard mode, a renamed private key or a key pasted into a config file is no longer sent.** Files were excluded only by name and location, so a key with a name such as `backup.conf` could have part of its content sent (the replacement of long alphanumeric strings does not apply to lines that contain `/`). JSON `"password": "…"` and tokens that contain `.`, such as JWTs, are now replaced too. （0.1.2）
- **Fixed: with "unrestricted", the protection against instructions planted in config files (removing invisible characters, defusing the data fence marks) was also turned off.** It is now always applied, whatever the setting. （0.1.2）
- **Fixed: the result of "Fix everything?" is shown in plain sentences instead of internal wording.** （0.1.2）
- **Added: have an LLM read your config files to find easily missed risks (LLM assist).** Files such as sudoers, cron and scripts are written in many different styles, so a program alone cannot always read them. The LLM looks for entries that involve root privileges (for example, a sudo setting that needs no password, or a file that root runs periodically). Before anything it finds is used in the analysis, PathScope checks that the line really exists in the original file. Before sending, you confirm which LLM will receive how many files. ## RoamSwitch Sensor

Software you install on your own general-purpose hardware (PC, Raspberry
Pi, etc., x86_64/arm64) — a separate product: pairing-code-based mutual
trust (fixed IP + short-lived code) with RoamSwitch-equipped endpoints
(Mac / Linux Client / Server Edition) for active vulnerability audits,
plus detection of new devices and spoofing on the LAN. Still under
development — see
<https://lafine.net/roamswitch-sensor-manual.html> for current status and
setup instructions.

### 0.4.2

- **New: the light audit of unmanaged devices can now check whether a device is a product with vulnerabilities in the CISA KEV catalog** (`unmanaged_audit.product_check`, **off by default**). It reads the product name from the web page a device normally returns and tells you whether that product has KEV-listed vulnerabilities. Covered: Fortinet FortiGate, Ivanti Connect Secure, Citrix NetScaler, Cisco (the ASA SSL VPN and the IOS XE web UI), UniFi OS, GeoVision, TerraMaster, Check Point Security Gateway and MikroTik RouterOS (Aruba devices have no entry in the KEV and are not covered).

### 0.4.1

- **New: detecting changes from each device's usual behavior** (on by default, `behavior.enabled`). The Sensor learns the hourly behavior of each device (identified by MAC, grouped by the existing device class) and reports unusual changes. It looks at bytes sent to public addresses, the number of public address ranges contacted for the first time, the number of LAN peers, DNS queries, data-carrying packets, and the ports used (including admin ports the device has never used). After the learning period (14 days by default, `behavior.learning_days`) it compares each hour with the past values of the same weekday-or-weekend hour (median and spread) and explains in words what changed compared with usual, such as "this camera used port 22 for the first time" or "outbound volume is 40 times the usual". Severity is low or medium, and **this finding alone never triggers lockdown or any other automatic blocking**. Sensitivity is `behavior.sensitivity` (low / normal / high).
- What it learns is stored in a state file (0600). Destination addresses are not stored, only a keyed Bloom filter. A new device that is still learning borrows the history of devices of the same class and reports only large changes. General-purpose devices such as PCs and phones are left out by default because their behavior changes by the hour (`behavior.include_general_purpose`). The CLI gained `behavior [--detail]`, `behavior reset <MAC>` and `network-threats`; the TUI gained a "Behavior baseline" tab. TUI text is in 10 languages and the CLI in Japanese and English.
- **Measured effect**: measured on simulated devices (cameras, printers, plugs, speakers, NAS boxes, IoT modules) and simulated anomalies. It has not been checked on real devices or real traffic. False alarms were about 0.05 to 0.09 per device per week at normal (about 0.44 for NAS boxes, caused by cloud-sync days). Detection at normal was 100% for a new port, 97% for LAN fan-out, 94% for a DNS surge, 83% for 3 a.m. activity and 100% for a surge of new destinations. Outbound volume increases were caught only 40% of the time (10%, 35% and 76% at 3x, 10x and 40x the usual) and are harder to see on low-traffic devices. A slowly growing upload was caught during the ramp 68% of the time.
- **Notes**: the thresholds were fitted to the simulated noise, so a real LAN may produce more false alarms; if so, set `behavior.sensitivity` to `low`. A device that was already compromised while it was learning has that behavior as its baseline. A Sensor on an access port sees only broadcast and multicast traffic. IPv6 and daylight-saving changes were not checked.

### 0.4.0

- **Added: detection of rogue DHCP servers (IPv4 and DHCPv6)**, on by default. Every hour (and on each `refresh`) the Sensor sends a single DHCP discover packet (a SOLICIT for DHCPv6) from a random MAC and counts every server that answers. It sends no request, so no address lease is taken. The first server it hears is learned as the legitimate one, and a server that appears later is reported. A server that hands out a gateway or DNS the legitimate one does not takes over where traffic goes, so it is critical. If several servers answer the first probe at once, none is learned and all are reported. `dhcp.allowed_servers` names the legitimate servers.
- **Added: IPv6 detection and support**, on by default. It reports router advertisements from anything other than the IPv4 gateway, an IPv6 address changing hands (NDP spoofing), and devices visible only over IPv6. The device inventory now holds IPv6 addresses (the `ipv6` CSV column, `ipv6_addrs` in JSON). The control API (50543) can also listen on IPv6 with `control.listen_ipv6` (off by default, applied on restart). Connection limits and lockouts count IPv6 per /64. A network whose IPv6 router is a different device from its IPv4 gateway is a normal case, so list that router in `ipv6.allowed_routers`.
- **Added: a light audit of devices without RoamSwitch**, opt-in and off by default. Only for devices inside the ranges the operator authorized, it makes TCP connections to a fixed set of 54 ports and reads what the services announce themselves. It does not attempt logins, exploit vulnerabilities, run nmap NSE or scan every port; deep diagnostics in the style of OpenVAS are done only to endpoints that agreed (paired). To enable it, first set `unmanaged_audit.authorization` (who approved it) and `unmanaged_audit.allowed_cidrs` (the ranges; IPv4 wider than /16 and IPv6 wider than /48 are refused). The device's MAC is checked before and after, and the run stops if the address changed hands. The authorization text is written to the operation log and the exports with every run. New: `audit-unmanaged <IP|MAC> --confirm` and `unmanaged-audits`, and in the TUI an "Unmanaged audits" tab and the `a` key.
- **Added: revocation and lockdown for a Sensor that is lost, stolen or retired.** After `revoke --reason` at the collector, that Sensor's uploads are refused with `403 sensor_revoked` (given only to requests with a valid signature), and the Sensor stops itself on its next upload. Locked down, it stops pairing, audits, uploads to the collector, notifications and probing of the network, and the control API answers only `sensor_locked_down`. The stop is stored in a file, so it survives a restart, and it stays in force if that file cannot be read. `security.on_revoked` chooses `lockdown` (default), `wipe` (overwrite with zeros and delete the keys, settings, paired endpoints, audit results and inventory, keeping only the operation log) or `none`. `security.lockdown_after_offline_days` stops a Sensor that has not reached the collector for that long (off by default). New: `lockdown on|off|status`, `decommission --confirm` and the `K` key in the TUI. `revoke` and `decommission` print the endpoints that were paired with the Sensor and how to unpair them.
- **Note: the endpoints that were paired with a revoked Sensor keep trusting it until each one removes the pairing.** A Sensor has no way to notify them (Linux: `roamswitch sensor unpair <this Sensor's public key>`; Mac: Settings > Sensor > Unpair). A Sensor carried off while powered down never receives the instruction to stop; disk encryption is the real protection.
- **Added: an `unmanaged` table in the evidence export** (CSV) and a light-audit section in the JSON and HTML reports. The inventory CSV has an IPv6 column. The collector dashboard lists revoked Sensors.
- **Verified with real packets.** On a throw-away Docker LAN, 35 checks cover DHCP and DHCPv6 servers, a rogue router advertisement, NDP spoofing, the light audit, the IPv6 listener, and revocation, lockdown, wiping and the offline stop (`scripts/lab/run.py`). It has not yet been checked under a real systemd (.deb) or on a physical switch. DHCP probing does not work on a Sensor connected over Wi-Fi; wired operation is assumed.

### 1.12.4

- **Added: a SUID / SGID file that appears or changes is now reported** (Server Edition; `suid_watch_enabled`, on by default). Turning on the setuid bit of a program the attacker controls is a common way to keep root, and it was one step of the BeyondTrust Remote Support zero-day intrusion (Mandiant, October 2026: web shell, then SUID enabled, then root). Critical-Path FIM watches a fixed list of files, so a new SUID file elsewhere, or SUID added later to an existing file, was invisible. Every `suid_watch_interval_secs` (default 600; 60 to 86400) the daemon walks the local filesystems and records the mode, owner, size and SHA-256 of every SUID / SGID executable (`/var/lib/roamswitch/suid_baseline.json`, 0600). The first inventory is the trusted state; after that, a new file, a bit added later, a changed mode or owner, or changed content is reported once as Critical and recorded in the incident timeline (ATT&CK T1548.001). A change that a package upgrade explains (the file belongs to a package and its change time is not later than the package database) is taken into the baseline without a notification. Container image layers (`/var/lib/docker` and the like), snap, and network, FUSE, overlay and squashfs mounts are not walked. `roamswitch fim verify` also prints these differences (exit status 1) and `sudo roamswitch fim update` accepts the current state.
- **Added: a log that is emptied, removed or replaced is now reported** (Server Edition; `log_tamper_watch_enabled`, on by default). Clearing the logs is the last move of most intrusions (ATT&CK T1070.002) and was part of the same intrusion; a log is supposed to change all the time, so FIM could not see it. Every 30 seconds the daemon checks `auth.log`, `secure`, `syslog`, `messages`, `kern.log`, `audit/audit.log`, `cron`, `dpkg.log`, `wtmp`, `btmp` and `lastlog`, and reports one that became smaller (it was 1024 bytes or more), disappeared or was replaced by a different file, unless log rotation explains it (the old file kept under another name, a fresh copy or compressed file next to it, or a logrotate status file updated within 2 minutes). The archived journal files (`system@….journal`) are reported when their total, at least 4 MiB before, falls below a fifth (for example `journalctl --vacuum-time=1s`). The active journal files are left out because journald preallocates 8 MiB for each of them.
- Measured on an Ubuntu 24.04 VM with a real kernel: a copy of bash with `chmod u+s`, a copy of a system binary with `chmod u+s` and `chmod u+s` on a package-owned file were all reported on the next walk (about 17 seconds); a package-owned file given the bit and followed by a package database update was taken in silently; `auth.log`, `syslog` (9 MB) and `dpkg.log` emptied or removed and the journal vacuumed were reported on the next 30-second look; a real `logrotate -f` was not. The first walk took 2 seconds for 20 SUID files. Not seen: files inside container image layers, a bit set and cleared again during a walk, changes made while a package manager is running (the walk is postponed up to 3 times), records of `wtmp` / `btmp` / `lastlog` rewritten without changing the size, and a decoy sibling file placed just before a wipe to look like a rotation.
- There are now 149 setting keys (112 in `server.conf` and 37 in `guard.yaml`; 3 new). The added wording is in 10 languages (based on machine translation, and not reviewed by native speakers).
- The bundled apps are unchanged (AccessScope 0.3.7, PathScope 0.1.9, PersonalSOC 0.1.14).

### 1.12.3

- **Fixed: on the Server Edition, a Docker container port published with `-p` could not be reached from outside, even when the port was in `allowed_ports` or `ssh_ports`.** The Default-Deny `forward` chain (`inet roamswitch_server`) is `policy drop` and accepted only established connections and traffic that did not arrive from the external interface. A published container port arrives from the external interface and is forwarded after DNAT, so a new connection to `-p 80:80` was dropped there, although the `DOCKER-USER` guard let port 80 through (found by connecting from another machine to a Docker host in a VM; a host that publishes containers only on `127.0.0.1` behind a reverse proxy was not affected). The `forward` chain now also accepts a new TCP connection that was DNAT-ed and whose original destination is an allowed port. Every other published port is still dropped, by the same `policy drop` and by the `DOCKER-USER` guard.
- Measured in a network-namespace test with DNAT of ports 80 and 8080 to a backend on port 80: before the change both were dropped; after it, port 80 passes and port 8080 is still dropped. In the VM, the `DOCKER-USER` drop counter rose for the not-allowed port. The Client Edition has no such chain and is not affected.
- The bundled apps are unchanged (AccessScope 0.3.7, PathScope 0.1.9, PersonalSOC 0.1.14).

### 1.12.2

- **Fixed: the lockfile and critical-path tamper notifications repeated with the same content every time the daemon restarted** (Linux client and Server Edition). The record of already-announced changes lived only in memory and was lost whenever the daemon started again, for example after a package update or a reboot. The baseline is deliberately never advanced on its own (so a possibly tampered change is not silently accepted), so the same notification came back at every start until `lockfile-fim update` or `fim update` was run. ## 1.12.1

- **Fixed: the honeytokens (decoy credential files) silently dropped every detection of a read.** To watch a decoy, the app itself holds the file open. On each detection it runs `lsof` to find who has it open, but the reader has usually exited by then, so only the app itself is left, and it was taken for the reader. A process of our own bundle counts as an "expected access", so the detection was dropped without a notification or a record. I installed the published 1.12.0 on a real Mac (a macOS 26 VM), confirmed that reading all five decoys produced no event at all, and then fixed it. The app's own process is now excluded, and when no reader is found it is reported as "could not be identified".
- **Fixed: the honeytokens missed every read of a decoy after the first.** macOS (APFS) updates a file's access time only on the first read after a write (a second `cat` of the same file leaves it alone), and kqueue reports no reads. A detection that looked at the access time every 30 seconds saw only the first read of a decoy, and when the app had read an existing decoy itself after a restart (to check it), it saw none of the attacker's reads. The access time is now set back to one second before the modification time at start, when a related decoy is added, and after every detection, so the next read moves it again. The kqueue notification caused by that is ignored for 2 seconds.
- On a real Mac (a VM), with the fixed build, the first read of a decoy, a second read of the same decoy, and a read of another decoy were all detected within 30 seconds.
- The Linux honeytokens use a different mechanism (fanotify) and were not affected by this (Linux 1.12.1 fixed a different missed-read problem).

- **Added: SSH brute force is now detected in real time and blocked.** On a Mac with Remote Login (sshd) enabled, it follows the unified log, counts failures, and uses pf to drop only new connections to the SSH port (by default 6 failures in 10 minutes; the first ban is 1 hour, a repeat offender gets 4 times as long, and the cap is 7 days). Established connections are not cut. The gateway, DNS, the Mac itself and loopback are never blocked, and the exclusion list, sources that succeeded with a public key (30 days) and sources of authenticated SSH sessions are exempt. Private IPs are not exempt. On a Mac with Remote Login disabled, the log is not read. It is on by default when Pro is activated. When fail2ban or similar is active, it only detects and notifies. Turning off the guard or blocking also releases all current bans, and the guard is part of the emergency recovery steps. **Brute force coming from IPv6 on the same LAN is not blocked automatically, so as not to cut off the whole LAN** (it is only recorded). Notifications are sent only when a ban is made and when a login succeeds after failures (critical). Added the read-only MCP tool `get_ssh_guard_incidents` (the Mac tools are now 33). Measured on a disposable macOS 26 VM: about 0.25 seconds from the 6th failure to the block.
  - The sshd log cannot be read by a standard user or by the sandboxed helper (measured), so it is read by a small root process (`--ssh-log-reader`) that starts before the sandbox and only launches `/usr/bin/log` with fixed arguments. Log lines are strings an attacker can write, so they are interpreted by a sandboxed parse worker running as `nobody`.
- **Added: FIM (critical file tamper monitoring) notifications now carry the SSH logins of the same period.** They show the owner and last modification, the SSH logins that started from 30 minutes before the change to about 1 minute after it (source, user, authentication method, time, and whether still connected), and sessions that had been running since earlier. **macOS does not tell which process wrote a file, so this is a coincidence in time, not proof of cause** (the notification says so too).
- **Fixed: the periodic log audit did not pick up SSH logins and failures on macOS 26.** On macOS 26 (OpenSSH 10), SSH login lines are written by `sshd-session`, not `sshd`. `sshd-session` is now covered too (matching by prefix would pick up the noise of unrelated `sshd-*` helper processes, so it is specified by name).
- **Added: an advisory score from a rewrite classifier in ransomware detection** (a port of the Linux edition's classifier). When a burst happens, 22 features are taken from the first, middle and last 4 KiB of up to the 20 most recent files, and a logistic regression computes a "ransomware-likeness" from 0 to 1. **On Mac it is advisory only.** The score is only kept in the log and in the saved alert, and the response does not change. If the model fails verification, it is not used (the existing decision stays). Bursts that touched canaries or honeytokens are not scored. FSEvents does not tell which process wrote, so the meaning of the inputs differs from Linux, and the Linux numbers do not carry over to Mac.
- **Fixed: the AI service diagnostic showed "usable from the network" even for services listening only on 127.0.0.1.** Only listeners reachable from the network are now diagnosed. It had the same construction as the bug confirmed on a real Linux machine, so Mac is fixed in the same way.
- **Added: a new finding `injection_exposure` (medium) in the MCP config audit (`audit_mcp_configs`).** It is reported once per file when the same config file has both a server that makes third-party text readable (web fetch, browser, search, chat, email, GitHub and so on) and a server that can run commands or change files. This is the arrangement that indirect prompt injection (ATT&CK T1698) depends on. The decision is only a match against known package and image names, and it does not look at what the servers' tools do or whether an AI follows instructions. Combinations across different files are not added up, and arguments, environment variables and tokens are not included in the result.
- **Changed: the bundled AccessScope is now 0.3.7, PathScope 0.1.9 and PersonalSOC 0.1.14** (see each app's entry for its changes). They also arrive through the in-app update. The Ubuntu handling works only on Linux, so of the PersonalSOC changes, the ones that concern Mac are the new notice for an OS package CVE matching that could not be completed, and the order of the Settings tabs.

## 1.9.6 - 1.9.54 (summarized)

Everything in these releases, grouped by topic. The full text of each entry is in the git history of this file.

- **Isolation (Air-Gap) reworked** (1.9.52, 1.9.23): what triggered an isolation decides how it ends. A tampered ransomware decoy, a confirmed XProtect detection and a manual isolation chosen from an ARP warning are "high confidence"; the rest (ClickFix, port anomalies, and so on) are "low confidence". Low confidence releases by itself after 10 minutes. High confidence does not: full isolation continues up to a limit (1 hour by default), then releases if the cause is confirmed gone, and otherwise moves to a "degraded mode" that keeps new connections blocked and never opens by time. Connections already open are cut when the isolation starts, and the state survives a helper restart. The Wi-Fi radio turned off by an isolation now comes back after an app crash or a restart (an independent watchdog, 1.9.23). (In 1.9.52 an isolation caused by ARP spoofing was not released automatically; 1.10.5 changed that.)
- **Ransomware** (1.9.50, 1.9.51): "Ransomware Recovery" (Pro) takes APFS local snapshots every 6 hours by default (off, 1, 3, 6, 12 or 24 hours), takes one at detection time, and pauses pruning for up to 7 days so the last generation before the encryption stays; recovery is manual, file by file, into `~/RoamSwitch-Recovered/`, never overwriting current files (needs Full Disk Access for the helper). The read-only MCP tool `get_ransomware_recovery_snapshots` lists the snapshots. The time from a decoy being tampered with to the emergency cutoff went from minutes to about 2 seconds (a code-signature check ran for every line of the open-files list).
- **Process execution recorder** (1.9.52, Pro): records process starts on this Mac only, with macOS's own `eslogger` (off by default, needs Full Disk Access), in a tamper-evident log; nothing is blocked. Seven behaviours notify (a browser, Office or mail app starting a shell; an unsigned binary run from a temp folder or with the quarantine flag; a download piped into a shell; `osascript` with base64 or eval; running a file right after its quarantine flag is removed; an unsigned binary started from a fresh launch agent; a non-Apple parent reading a keychain secret). Banners only for high severity and at most once per kind every 10 minutes; "Allow this program" allows one keychain item. MCP tools `search_exec_events` and `get_process_tree`.
- **Port scans and unknown ports** (1.9.32, 1.9.44 to 1.9.49, 1.9.54): automatic detection and 10-minute blocking of nmap/masscan-style scans (Pro); the block cannot be abused with a forged SYN claiming the gateway's address (only new inbound TCP is refused, and the gateway, DNS resolvers and the Mac's own addresses are exempt), detection no longer stops after start-up (`pflog0`), and a flood of forged SYNs can no longer fill pf's state table. Listeners of root programs are now seen through the privileged helper and read through libproc (about 2.4 ms against 16 ms for `lsof`, every 2 seconds); a signed executable swapped for an unsigned one with the modification time restored is noticed; UDP listeners from interpreters or unsigned programs are reported; alerts name the real program behind `python3` or `node`.
- **Active vulnerability checks and logs** (1.9.44, 1.9.53): unauthenticated Elasticsearch, CouchDB, Jenkins and VNC, SMBv1 and SMB signing were added; the CSV export explains safe and inconclusive results correctly, and every scan has an ID and a locked log.
- **RoamSwitch Sensor** (1.9.32 to 1.9.37, 1.9.52): mutual pairing moved from mDNS to a pairing code; an active audit can be requested from a Sensor and its result fetched later (MCP tool `get_sensor_audit_results`); with a pinned certificate fingerprint everything runs over TLS with Sensor 0.3.9 or later; a crash of the privileged helper on every successful pairing was fixed.
- **Supply chain and secrets** (1.9.27 to 1.9.30): dependency-lockfile tamper monitoring, install-script inventory, npm signature and provenance checks, the `roamswitch-npm` wrapper that runs installs in a network-denied sandbox, typosquat detection by edit distance, and detection of leaked crypto-wallet seed phrases and private keys (checksum-verified). Pro.
- **Log audit and notifications** (1.9.6 to 1.9.26): notification history for the past 7 days; Automatic Log Audit (Pro) scanning hourly for new patterns and frequency spikes, with each template compared against its own history; ClickFix-style commands on the clipboard (including the Script Editor pivot). Many false positives were removed (CoreAudio, loginwindow, `PersistentAppsSupport`/`BTMManager`, `CFPasteboardRef`, pointer addresses), notifications explain in plain language whether action is needed, EICAR test hits no longer raise a notification, and the log-audit window's cards became clickable.
- **Critical Path FIM** (1.9.16, Pro): SHA-256 baseline monitoring of files such as `/etc/sudoers`, SSH configuration, `/etc/hosts` and root's `authorized_keys`.
- **Reports that assumed success** (1.9.19): four items that reported success without confirming anything (automatic dev-server port blocking, malware-quarantine moves, the "macOS Accessory Connection Protection" check that was hard-coded to pass, Critical Path FIM helper-connection failures) now show the real outcome.
- **Updates and languages** (1.9.26, 1.9.34 to 1.9.43): the privileged helper is reliably restarted on update; warning bursts and a false "/etc/hosts tampered" warning right after an update were fixed; update prompts bring the app to the front; shared-service stop/restore checked `launchctl` exit codes; Link Guard's homograph detection and the ransomware guard's MITRE ATT&CK ID compared translated strings instead of a language-independent value, which broke them in most languages other than Japanese, English and French. CSV headers, the package-CVE tabs and several texts were fixed in all 10 languages.
